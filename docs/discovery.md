# Repository discovery

The first V3 discovery slice supports the bundled, read-only `backend/examples/commerce-system` repository. From `/projects/import`, an authenticated user creates a private project and Production environment, queues a scan, reviews a preview, and explicitly applies it. The project exists while review is pending, but no discovered topology is stored until Apply. Owners can also connect the same demo to an existing project from Integrations.

`RepositoryScanWorker` processes persisted queued jobs outside the HTTP request. Scan and job status, counts, warnings, failure, and history remain in PostgreSQL. A restart marks interrupted Running scans as Failed so they can be retried. Only one active scan per connection is allowed. There is no scheduled polling in this slice.

`IDiscoveryParser` returns normalized component and dependency candidates and warnings; it does not write to the database. The Docker Compose parser uses YamlDotNet and recognizes `compose.yaml`, `compose.yml`, `docker-compose.yaml`, and `docker-compose.yml`. Services become candidate components. Image-name heuristics identify common databases, brokers, and caches; all others start as Service. Sequence and mapping forms of `depends_on` become directed Infrastructure dependencies. Source paths and `services.<name>.depends_on` locations are retained as evidence. Heuristic type is a starting point, not a claim about runtime behavior.

The scanner limits a file to 2 MB, a Compose document to 500 services, YAML nesting to 48 levels, and YAML events to 100,000. It rejects aliases, skips symlinks and common generated directories, and never executes repository files. It stores normalized preview data, not a copy of the repository. Parser warnings are visible in the preview and scan history. The current source is a fixed bundled path, so the API does not accept arbitrary local paths or URLs.

Apply reconciles by repository connection plus stable `source path:service key`. New components and dependencies are inserted once; rescans update discovered metadata and mark missing discovered components `Missing` instead of deleting them. Manual name and type corrections survive rescans. A same-name component from another source is reported as a conflict and skipped. Dependency evidence is stored separately; existing V2 dependency source values are backfilled into evidence rows by the V3 migration. The V2 `Dependency.Source` column remains for compatible queries.

Current limits: only the bundled repository and Docker Compose parser are wired. Generic Git cloning, Azure DevOps, Kubernetes, OpenAPI, and pipeline YAML require later slices. Compose `depends_on` describes startup configuration and does not prove a live runtime call. Unknown service references become warnings. A scan does not delete dependencies that disappear from a later file; missing-component status is the current review signal.
